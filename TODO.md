Statuses reflect evidence available on 7 October 2026. The application modules, selected Supabase schema/seed, and cross-role attendance workflow are verified. Only the managed permanent website publication remains open until its checkpoint and deployment are confirmed.

## Product identity and access

- [x] **BITS Kurnool identity:** Use “Brindavan Institute of Technology & Science”, compact name “BITS Kurnool” or “BITS KNL” in constrained space, the user-supplied BITS seal, official website https://www.bitskurnool.edu.in/, and address “NH-7, Peddatekur, Kurnool – 518218, Andhra Pradesh, India” consistently in the login, dashboard, profile/about/settings and app branding.

## Student experience

- [x] **Student module:** Student access includes Dashboard, Profile, Attendance, Timetable, Subjects, Examinations, Results, Fees, Notices, Notifications, Assignments, Events, and Help/Support.
- [x] **Student dashboard:** Show student name, roll number, department, year, section, attendance, today’s classes, upcoming exam, pending fees, and quick actions for Attendance, Timetable, Exams, Results, Fees, Notices, and Notifications.
- [x] **Student attendance:** Show overall attendance, subject-wise attendance, attendance history, and monthly chart; include status examples DBMS 92%, OS 84%, CN 79% where applicable, with Green=Good, Amber=Warning, and Red=Critical.
- [x] **Saved faculty attendance is student attendance:** Student attendance reads the records saved by faculty through the REST API/PostgreSQL workflow, rather than a separate hard-coded frontend dataset.

## Faculty attendance and academics

- [x] **Faculty module:** Faculty access includes Dashboard, My Classes, Students, Attendance Register, Marks, Timetable, Class Notices, Notifications, and Profile.
- [x] **Attendance-register workflow:** Faculty Login → Faculty Dashboard → My Classes → select Department → Year → Section → Subject → Attendance Register → select Date → load assigned students → mark Present/Absent/Late → save Attendance. Faculty can only access assigned classes.
- [x] **Register presentation and controls:** Display subject, department, year, section, faculty, date, total students, roll number, student name, attendance status, and attendance percentage; include Mark All Present, search by student name/roll number, All/Present/Absent/Late filters, and live Total/Present/Absent/Late/Attendance % counters.
- [x] **Attendance save confirmation and effects:** Before saving, show Confirm Attendance with Total, Present, Absent, Late, Date, and Subject; provide Cancel and Confirm & Save. Persist the session and records in a database transaction, recalculate subject attendance, update the student read view and HOD analytics, record an audit event, and generate a low-attendance notification when the configured threshold is crossed. Show “Attendance saved successfully” after success.
- [x] **Attendance history and edits:** Faculty can view previous records with Date, Subject, Section, Present, Absent, Late, and Percentage; editing is limited to authorized recent records.
- [x] **Marks and results:** Support faculty marks entry, HOD review, authorized publication, and student visibility of published examination results.

## Administration and communication

- [x] **Admin operations:** Admin access includes Dashboard, Students, Faculty, Departments, Courses, Subjects, Sections, Attendance, Examinations, Results, Fees, Notices, SMS, Notifications, Reports, Audit Logs, and Settings; admin CRUD operations enforce validation and audit sensitive changes.
- [x] **Role-scoped notices and notifications:** Admin publishes college-wide notices; HOD publishes department notices; Faculty publishes assigned-class notices; Students read notices. Notice publishing fans out in-app notifications with read-state updates.
- [x] **SMS architecture:** Admin can create a campaign, select audience, compose a message, and inspect mock/queued recipient state. Use a provider-agnostic adapter and safe mock mode when gateway credentials are absent; do not transmit real SMS without configured credentials.
- [ ] **Parent SMS data model, authorization, and audit:** Add persistent PostgreSQL parent-SMS campaigns with department/section scope and per-student delivery records. Faculty can send only to parents of students in sections assigned to that faculty member. HOD can send to a section or the HOD's own department. Enforce scope on the server, show recipient counts rather than phone numbers, store campaign/per-student delivery status, and write an audit event. Restrict campaign history to the sender or authorized HOD department.
- [ ] **Parent phone privacy and consent:** Keep all new student records opted out by default. Only Admin/Super Admin can record or withdraw parental opt-in, and recording opt-in requires an existing parent phone. Never display parent phone numbers in dashboard clients. In gateway/live mode, only non-demo students with an Admin-recorded parent opt-in and a valid phone may receive SMS; fail closed when gateway configuration is incomplete. Mask phone values in stored recipient records and logs.
- [ ] **Faculty/HOD Parent SMS clients:** Provide responsive web and Expo mobile Parent SMS interfaces for Faculty and HOD with authorized audience/scope selection, message composition, recipient-count preview, explicit review/confirmation before send, safe mock/live warnings, and authorized campaign history. Do not expose Parent SMS navigation to Student, Principal, or Admin roles; keep Admin institution-wide SMS campaigns separate.
- [ ] **Provider-safe Parent SMS delivery:** Reuse a provider-agnostic SMS adapter with mock mode as the default and no network transmission unless a server-side HTTP gateway URL, key, and sender ID are configured outside source code. The configured gateway request uses JSON `{to,message,sender}` and Bearer-key authentication; adapt providers on the server rather than exposing credentials to web/mobile clients.
- [x] **Other operational records:** Provide database-backed examinations, fees, timetable, assignments, events, reports/CSV export, audit logs, and notification records, with role-scoped API access.
