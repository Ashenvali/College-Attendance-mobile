# BITS Kurnool — full project audit, 6 November 2026

**Scope:** every tracked file in this repository (126 files at audit start; `apps/api`, `apps/web`, `apps/mobile`, `scripts`, `docs`, root configuration).
**Method:** source inspection + executable evidence. A disposable PostgreSQL 16 instance was created in the audit sandbox, the checked-in migrations were applied, the demo data was seeded, and the real HTTP API, the web production build and the Expo export were run. Nothing in this document is inferred from a screen or a button existing — every PASS has a file path and an observed result.

**This report is evidence-based and is allowed to say "not verified".** Items that need a physical Android device, a live SMS gateway, a Play Console account, or legal review are marked **NOT VERIFIED** and are not counted as complete.

## G. Security findings

1. **Error responses leaked secrets (CRITICAL, fixed).** Any PostgreSQL constraint violation returned `error.message` with the full SQL and bound parameters — including a bcrypt hash and parent phone number. `server.ts` now maps `23505/23503/23502/22P02` and logs the raw text server-side only.
2. **Sign-out was cosmetic (HIGH, fixed).** Tokens remained valid for the full 8 hours. Every token now carries `sessionVersion`; logout/revoke/password change/admin reset increment it, and `requireAuth` rejects stale versions. Deactivation (`users.active`) was already enforced.
3. **Demo credentials on the login screen (MEDIUM, fixed 7 Nov).** Five fictional accounts were listed and auto-filled in `apps/web/src/components/LoginScreen.tsx`. They are now shown only when the API reports `demoMode:true`; with `DEMO_MODE=false` the panel disappears and demo sign-in returns `403`. Still run `npm run db:disable-demo` against the production database.
4. **Bearer token in `sessionStorage` (MEDIUM, by design).** XSS on the portal would expose it. There is no user-content `dangerouslySetInnerHTML` in the app today (only the new static `<style>` in `+html.tsx`), so the exposure is limited to the origin. Consider httpOnly cookies when a real identity provider is added.
5. **Dependency advisories (MEDIUM, open).** 3 high / 8 moderate, all in the Expo build toolchain (`expo-router`, `query-string`, `esbuild`, `glob`, `minimatch`, `drizzle-kit`). None are in the API's production dependency tree. Fix by upgrading the Expo SDK deliberately, not by `npm audit fix --force`.
6. **RLS is a deny-all for Supabase's REST roles (LOW, intentional).** Migration `0002` enables RLS on every table and revokes `anon`/`authenticated`. That is correct because all traffic goes through the Express API (which connects as the table owner and enforces RBAC), but it means: never expose Supabase's REST endpoints to clients, and re-run the migration after adding tables.
7. **Rate limiting outside login (LOW, partly fixed).** SMS send/retry routes now have a per-staff limiter (`SMS_RATE_LIMIT_PER_MINUTE`). Attendance saves are still unthrottled; they are protected by RBAC, the 7-day edit window and unique constraints, so the residual risk is low.
8. **No MFA and no password policy beyond length (LOW, open).** Staff accounts (HOD/Principal/Admin) with real data should require MFA.
9. **Positively verified:** no service-role/SMS keys anywhere in source or client bundles; parameterised SQL everywhere (a manual injection probe was rejected); 28/28 role-permission checks; login throttling (10 attempts → 429); `verify-full` TLS for Supabase; audit logging of sensitive staff actions.

## H. Launch readiness decision

# NOT READY FOR LAUNCH

**The application itself is closer to ready than a typical first audit: the backend is genuinely functional and verified end-to-end. What blocks launch is not primarily code — it is the release, legal, and device-testing work that must be done by the college.**

Why:

1. **Nothing has run on a real Android device.** The bundle compiles, but no build has been installed. The Android back button, keyboard behaviour, small-screen layout, and real network conditions are unverified.
2. **Production configuration is still placeholder.** `apps/mobile/eas.json` contains `REPLACE-WITH-PRODUCTION-API-HOST`. A build with that value fails at the first request.
3. **No live SMS.** The whole parent-notification feature is mock-only until a DLT-registered sender/template and gateway key exist. Sending real SMS from an unregistered sender in India is not permissible.
4. **Legal/administrative items are missing:** published privacy policy, terms, Data Safety form, retention/deletion policy, and written college authorisation to publish.
5. **Demo credentials were displayed on the login screen.** Fixed on 7 Nov: `DEMO_MODE` decides whether they exist at all, and the store build profile sets it to `false`.
6. **Password reset does not exist**, so real users who forget a password cannot recover without an administrator.

**What it *is* ready for today: READY FOR INTERNAL TESTING** — the web portal plus the `/mobile/` browser build run against a real PostgreSQL database, with RBAC, attendance and mock SMS verified. Use it for staff walkthroughs and UAT with the clearly labelled demo data.

## J. Final recommendation

**1. How complete is the project, honestly?** About **80% of the software** and **0% of the release process**. The API, database, attendance engine, RBAC and mock SMS pipeline are real and were verified by execution. The last 20% is the unglamorous half: password recovery, profile maintenance, live SMS, push notifications, and device-proven behaviour.

**2. What is missing?** Password reset/recovery, student profile editing, faculty/admin account-lifecycle UI, FCM push, SMS cost tracking, dark mode, PDF/Excel reports, automated backup/restore, CI, ESLint, terms of service, published privacy policy, Play listing assets, DLT registration.

**3. What is broken?** Nothing crashes in the flows exercised today. Two things *were* genuinely broken and are now fixed: the mobile app could not run in a browser at all, and error responses leaked database detail. Two things remain broken by design and must be changed before production: placeholder API hosts in `eas.json` (`REPLACE-WITH-…`) and demo credentials on the login screen.

**4. What must be fixed before real users can use it?** In order: real API URL in the release profile, demo accounts removed, password recovery, a device test pass, live SMS with DLT registration, and a published privacy policy with college authorisation.

**5. Can you safely release it to students and faculty?** **Not today.** You can safely demo it (as it is now) and let staff evaluate the portal and the `/mobile/` browser build with fictional data. Handing it to real students with real attendance and real parent phone numbers requires items 1–7 of the fix plan.

**6. Final steps before publishing:**
1. Deploy the API + portal (the `Dockerfile` already builds both, including the mobile web export) and set `DATABASE_URL`, `BITSKNL_AUTH_SIGNING_SECRET` (32+ chars), `NODE_ENV=production`, `TRUST_PROXY`.
2. Run `npm run db:migrate` on Supabase, verify RLS in Advisors, then `npm run db:disable-demo`.
3. Set the production `EXPO_PUBLIC_API_URL`, build the AAB with EAS, install it on at least three real devices and complete the test matrix.
4. Register the DLT template, run the SMS pilot with one consenting guardian, then enable `manual` mode for one department.
5. Publish the privacy policy and terms, complete the Data Safety form, create the store listing and a reviewer account.
6. Obtain written college authorisation and logo permission, then submit to the Internal testing track, then Production.
